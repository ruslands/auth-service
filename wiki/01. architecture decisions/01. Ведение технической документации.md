
### **Контекст**  
Для эффективного управления документацией в проекте необходим структурированный подход, обеспечивающий прозрачность, согласованность и удобство внесения изменений.  

### **Решение**  
Мы внедряем следующую систему работы с документацией:  

- **Формат**:  
  - **Markdown (`.md`)** – для текстового контента, диаграмм и визуальных схем.

- **Диаграммы**: 
 - Для создания диаграмм и схем используем [mermaid](https://mermaid.js.org/intro/getting-started.html) этот инструмент поддерживается в Obsidian.

- **Хранение**:  
  - Вся документация размещается в **Git**, обеспечивая контроль версий и совместную работу.  

- **Процесс внесения изменений**:  
  1. Склонировать репозиторий:  
     ```bash
     git clone git@git.seller-1.ru:rtk/backend.git 
     ```  
  2. Внести изменения локально с помощью [Obsidian](https://obsidian.md) или другого Markdown-редактора.  
  3. **Обязательно отрефакторить текст через GPT** (проверка ясности, логики и оформления).  

  4. Создать **отдельную ветку** и отправить изменения:  
     ```bash
     git checkout -b wiki/update-docs
     git add .
     git commit -m "Обновление документации"
     git push origin wiki/update-docs
     ```  
  5. Оформить **pull request** для ревью перед слиянием.  

- **Требования к авторам документации**:  
  - Базовое знание **Git** (работа с ветками, коммитами, pull request'ами).  
  - Соблюдение структуры хранения файлов.  
  - **Обязательное использование GPT** для улучшения качества текста.  
  - Проверка Markdown на соответствие стандартам перед отправкой.  

### **Структура документации**  
Документация разделена на несколько ключевых разделов:  

- **ADR (Architecture Decision Records)** – фиксация принятых архитектурных решений.  
  - [Руководство по ADR](https://github.com/joelparkerhenderson/architecture-decision-record)  
  - [Шаблоны ADR](https://adr.github.io/adr-templates/)  

- **Сервисы** – описание создаваемых сервисов:  
  - **API** – спецификации API.  
  - **PDM** – управление зависимостями и пакетами.  
  - **Sequence** – последовательность выполнения процессов.  

- **Технические решения** – документация по техническим решениям, не влияющим на архитектуру, но важным для команды.  

### **Последствия**  
- **Структурированность** – единые принципы ведения документации.  
- **Контроль версий** – история изменений всегда доступна.  
- **Прозрачность и удобство работы** – простой процесс ревью и коллективного редактирования.  
- **Гибкость** – легко адаптируется под нужды команды.  
- **Качество** – благодаря обязательной проверке через GPT документы остаются четкими и читаемыми.
