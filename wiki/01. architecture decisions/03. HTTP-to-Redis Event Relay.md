# HTTP-to-Redis Event Relay

## Overview
The **HTTP-to-Redis Event Relay** is a lightweight, dedicated service that receives events via HTTP and reliably publishes them to Redis channels or streams. It decouples external event producers from internal systems, ensuring message delivery even when core services are temporarily unavailable.

---

## Problem

1. **Main Service Unavailability**
   - When the main application or processing service is down (e.g., due to deployment, crash, or maintenance), incoming events (webhooks, API calls, etc.) are lost.
   - There is no buffer or independent handler for external systems trying to send event data.

2. **Restricted Access to Redis**
   - External systems cannot connect directly to Redis due to security, network isolation, or architectural constraints.
   - There is a need for a secure, controlled HTTP endpoint that acts as a bridge to Redis.

---

## Solution

The **HTTP-to-Redis Event Relay** acts as a resilient middle layer with the following responsibilities:

- **Accepts HTTP POST requests** from external sources (e.g., webhooks, sensors, microservices).
- **Parses and validates** incoming events based on predefined schemas or lightweight rules.
- **Publishes events to Redis** (via Pub/Sub channels or Redis Streams) in real-time.
- **Runs independently** from the main service to ensure high availability and continuous ingestion.
- **Can be scaled horizontally** and secured via API keys, firewalls, or rate limiting.

---

## Benefits

- Prevents data loss during main service downtime.
- Simplifies external integration (HTTP endpoint instead of direct Redis access).
- Enables event-driven architectures and better system decoupling.
- Can be easily monitored, logged, and extended (e.g., for retries, dead-letter queues).

---

## Example Flow

1. External service sends `POST /events` with JSON payload.
2. Event Relay receives and validates the request.
3. Event is published to a configured Redis channel (e.g., `events.user_signup`).
4. Downstream services subscribed to Redis receive and process the event.

---

## Future Improvements

- Add buffering/retry mechanism (e.g., with local queue or Redis Stream).
- Support multiple event types and routing rules.
- Add metrics, health checks, and alerting.
