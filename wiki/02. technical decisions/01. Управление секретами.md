## **Цель**  
Обеспечить **безопасное хранение и управление секретами** (пароли, API-ключи, токены, конфиденциальные данные) для различных окружений.

## **Проблема**  
При загрузке секретов из **Secret Manager** на этапе билда с использованием **Terraform** существует **ограничение в 4 КБ** на объем передаваемых данных в переменную окружения. Это ограничение препятствует хранению всех необходимых секретов в Secret Manager. (Yandex Cloud Limits)[https://yandex.cloud/en/docs/functions/concepts/limits]

## **Решение**  
Для решения проблемы используется сочетание методов хранения конфигурационных данных:  

1. **.env файл** в репозитории Git содержит **общие для всех окружений конфигурационные переменные**.
2. **Secret Manager** применяются для хранения **специфичных для окружения конфигурационных переменных**, которые должны быть защищены.
3. **GitLab Variables** содержит переменные для доступа к Secret Manager: SECRET_ID под каждое окружение и YANDEX_SERVICE_ACCOUNT_ID, YANDEX_AUTHORIZED_KEY_ID, YANDEX_PRIVATE_KEY_BASE64

## **Локальная разработка**
Два варианта:
1. Добавить в **.env файл** переменные окружения, которые укажены в Secret Manager и модифицировать их под локальную разработку, например POSTGRES_URI.
2. Добавить в переменные окружения локальной машины SECRET_ID, YANDEX_SERVICE_ACCOUNT_ID, YANDEX_AUTHORIZED_KEY_ID, YANDEX_PRIVATE_KEY_BASE64. В этом случае приложение прочитает переменные из Secret Manager.

## **Альтернативные решения и их ограничения**  


| **Метод хранения**                                     | **Описание**                                                                                                                                                                        | **Плюсы**                                                                                                    | **Минусы**                                                                                                                                                                   |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Secret Manager + .env**                              | - **Secret Manager** хранит **чувствительные данные** (пароли, ключи шифрования, API-токены). <br>- **.env-файлы** (Git) содержат оставшиеся конфигурационные переменные.           | - Централизованное хранение чувствительных данных и конфигураций. <br>- Простота и безопасность.             | - Лимит 4 КБ на данные в Secret Manager через Terraform. <br>- Необходимость хранить `.env`-файлы в Git (может быть риск утечек). <br>- Нет автоматической ротации в `.env`. |
| **Использование только Secret Manager**                | - Хранит все секреты, включая чувствительные данные, до 4 КБ. <br>- Загружается через Terraform. <br>- Поддерживает автоматическую ротацию и контроль доступа.                      | - Централизованное хранение и автоматическая ротация. <br>- Безопасность через IAM.                          | - Ограничение в 4 КБ на загрузку через Terraform. <br>- Запросы могут замедлять приложение. <br>- Высокие затраты на частые обращения.                                       |
| **Использование только .env-файлов**                   | - Хранятся в Git, содержат конфигурационные данные, не попавшие в Secret Manager (настройки хоста, порта, домена, логирование и т.д.). <br>- Загружаются в приложение через dotenv. | - Простота в использовании. <br>- Легко версионировать в Git. <br>- Быстрое локальное изменение переменных.  | - Хранение в Git увеличивает риск компрометации. <br>- Нет автоматической ротации секретов. <br>- Требуется дополнительное шифрование для безопасности.                      |
| **Consul + HashiCorp Vault**                           | - Полная безопасность, поддержка динамических секретов. <br>- Гибкое управление доступом. <br>- Требует дополнительной настройки.                                                   | - Полная безопасность и поддержка динамических секретов. <br>- Гибкость в управлении доступом.               | - Сложность настройки и поддержки. <br>- Требует дополнительных ресурсов. <br>- Не подходит для небольших проектов.                                                          |
| **Использование Kubernetes Secrets**                   | - Хранение секретов в Kubernetes. <br>- Управление через Kubernetes API.                                                                                                            | - Удобно для приложений в Kubernetes. <br>- Управление через стандартный API.                                | - По умолчанию не шифруются, требуется дополнительное шифрование. <br>- Доступ ограничен только Kubernetes.                                                                  |
| **Хранение секретов в Terraform (без Secret Manager)** | - Секреты хранятся в Terraform, инфрастуктурный код полностью определяет секреты.                                                                                                   | - Нет необходимости делать запросы к внешним сервисам. <br>- Инфраструктурный код управляет всеми секретами. | - Секреты попадают в стейт-файл Terraform, что может привести к компрометации. <br>- Нет механизма ротации. <br>- Увеличивает сложность управления чувствительными данными.  |
